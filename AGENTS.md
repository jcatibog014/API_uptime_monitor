# AGENTS.md

This file guides AI coding agents (Claude Code, Codex, Cursor, Copilot and others) working in this repository.

## Overview

**Pulse Check** ("Is your API still breathing?"), an API uptime monitor in Python (Flask). The repo is `API_uptime_monitor` and the Python package is `pulsecheck`. The owner adds monitors (addresses to check); a background crew checks each one on a schedule, times every part of the answer, opens an incident when a service really fails, and sends alerts that are tried again until they arrive. The plan is `docs/PLAN.md`.

It is a learning project for **scheduled jobs, metrics, alerting and failure handling**, so those parts stay easy to read: short comments that explain *why*, a job queue written by hand (no Celery, RQ or Redis), checks written with Python's own socket/ssl/http.client (no requests), login written by hand (no Flask-Login), and no extra libraries unless the owner asks for them. Write the README in simple (A1-level) English.

## Architecture

- **The login cookie is `pulsecheck_session`, not Flask's `session`:** browsers keep cookies per host, not per port, so the owner's other Flask apps on 127.0.0.1 overwrote it and logged Pulse Check out on the next click (`tests/test_auth.py::test_another_local_apps_cookie_doesnt_log_you_out`).
- **Accounts (`auth.py`):** no sign-up (an open sign-up could be misused to hammer other people's sites from ours). The OWNER is made from the PC with `create-owner` (one per site); everyone else uses Try Demo. Hashes from Werkzeug; 5 wrong passwords lock the account for 15 minutes, one address may try 30 logins per 15 minutes (`limits.py`). `load_user()` checks `session_version` on every request (a password change logs out other devices) and puts `g.user` and `g.workspace` on the request.
- **Workspaces:** every row that belongs to someone has `workspace_id` (or hangs off a row that does: a check off its monitor). Queries in views always filter by `g.workspace.id`; `monitors.get()` gives a 404 for anyone else's monitor.
- **The private-network guard (`targets.py`), read it before touching probing:** a monitor makes the SERVER call an address and shows the answer, so an unguarded one could read the cloud metadata service (169.254.169.254) or a private database (SSRF). `url_problem()` checks an address when it is saved (http/https, a host, no password in it, no private IP or name like `localhost`/`.internal`). At check time `probe.py` looks the name up ITSELF, keeps only addresses `allowed_ip()` accepts (`ip.is_global`; IPv4-mapped IPv6 unwrapped) and connects to that exact address, so DNS rebinding can't swap it. Every redirect is checked the same way. `ALLOW_PRIVATE_TARGETS` turns the guard off for your own PC and tests; `create_app` refuses it on Render.
- **Probing (`probe.py`):** `check(url, method, expected, timeout, allow_private, resolver, clock)` never raises; it returns a `Result` with `ok`, `error_kind` (dns, blocked, refused, timeout, tls, connection, redirects, http_status), a plain `message`, `status_code`, `remote_ip`, the times of each part in ms (`dns_ms`, `connect_ms`, `tls_ms`, `ttfb_ms`, `total_ms`; with redirects the parts add up), at most 64 KB of the body, the headers, and the certificate's expiry and issuer. One deadline covers the whole check. Status rules are text like `200-299, 404` (`parse_statuses`). The User-Agent is `PulseCheck/1.0 (uptime monitor)`.
- **Checks (`checking.py`):** `PROBERS[kind]` picks the prober for a kind of monitor; `run_check()` probes and `record()` saves a `Check`. `checks` is UNIQUE(monitor_id, scheduled_at): the moment a check was MEANT for. A check made twice for one moment is saved once (a savepoint catches the race), which is what makes at-least-once jobs safe. Check now (`views/monitors.py`) uses the same path, 6 a minute per workspace.
- **The job queue (`queue.py`), ported from Right On Cue:** a `jobs` table written by hand (no Celery/RQ/Redis). `enqueue()` (a UNIQUE `dedupe_key` makes the same work exist once; a savepoint catches a race), `claim()` (PostgreSQL `FOR UPDATE SKIP LOCKED`, plus a guarded `UPDATE ... WHERE status='queued'` checked by rowcount on both), leases (120 s, longer than the longest check; `reap()` puts back a dead worker's job: at-least-once, so every handler must be safe to run twice), `Retry` (exponential backoff with full jitter, 30 s up to 1 h, or the service's Retry-After), `Defer` (wait without using a try), `GiveUp`, dead letters after `max_attempts` with `retry_now()` / `discard()`. Handlers are registered with `@queue.handler(kind, on_dead=...)` and get `(s, job, now)`. `run_job()` calls `s.expire_all()` first: a worker's session lives for many jobs.
- **The schedule (`scheduler.py`), the scheduled-jobs lesson:** each monitor has `next_check_at` on its own timetable: slots `EPOCH + offset + k * interval`, where `offset_of(id, interval)` spreads monitors over the minute. `run_due()` claims each due monitor with a compare-and-swap (`UPDATE ... WHERE next_check_at = <read>`) and queues a `check` job (dedupe key: monitor + slot). NO DRIFT: the next check is the next slot, never "now + interval". A slot more than one interval late (the site slept) is skipped and recorded as a `Gap` (uptime leaves gaps out); only the latest due slot is checked. The `check` job commits before probing (no transaction open during a 30-second wait), records the check, then runs `after_check` hooks. `schedule()` plans a new or resumed monitor straight away, a changed interval onto its new timetable, and a paused one to None.
- **The crew (`worker.py`):** a round = reap, `every_round` tasks, `scheduler.run_due()`, `queue.work()` (3 jobs a round), heartbeat (`workers.last_seen`). The web app runs `CREW_SIZE` (4) worker threads, so one slow check holds up only its own thread. A worker sleeps until the next due check / job / lease (`wake_ups` hooks add moments), at most 5 minutes; `nudge()` wakes them (a new monitor, Resume). `flask worker` runs one in its own process. `simulate(s, start, until)` plays time forward from due moment to due moment without waiting: tests use it, and so does the demo. Check lag (started minus scheduled) is shown on the Crew page (`views/crew.py`) with workers (On Duty / Gone Quiet / Off Duty), queue counts, dead letters (Retry now / Discard) and gaps.
- **The timer (`tick.py`, `.github/workflows/tick.yml`):** `POST /tasks/tick` with `X-Tick-Key` (404 otherwise) every 10 minutes wakes the site if it slept, runs worker rounds until nothing is due (25 s at most), and tidies (`tidy_jobs` hooks; finished jobs after a week, stopped workers after a day, old rate-limit windows).
- **Failure handling (`incidents.py`), the failure-handling lesson:** `judge()` runs after every check (scheduled, re-check or Check now) through `scheduler.after_check`. States: Waiting -> Steady (or Weak Pulse) -> Irregular on a failure (a quick re-check 20 s, then 40 s later, unless the regular check comes first) -> Flatline after `confirm_tries` (3) failures in a row, which opens an `Incident` dated from the FIRST failure. An incident closes after `recover_tries` (2) good checks in a row (a good check during an incident asks for a quick re-check). `judged_until` skips a check older than (or the same as) one already judged, so at-least-once jobs and late re-checks never count twice. `Monitor.version` is a SQLAlchemy `version_id_col`: the check job (`scheduler.check_slot`) catches StaleDataError (a page changed the monitor during the check), reads it again and judges again. Hooks: `on_open`, `on_resolve`, `on_move` (alerts use them). Pausing keeps an open incident; resuming resets the streaks.
- **The canary (`canary.py`, `timers.py`):** once a minute one worker (a `timers` row claimed by compare-and-swap) queues a `canary` job that checks our own address (`BASE_URL/healthz`; on Render this counts as a visitor, so the free plan never sleeps) and `CANARY_URL` (an outside page that is always up). While the outside check is failing (`our_side_down`, results fresh for 3 minutes), a failed http check is marked `our_side` and judged no further: one blip on our server must not page you for every service. Tests have no canary unless they ask (`SELF_CHECK`, `CANARY_URL`); the Crew page shows both checks. Canary rows are kept 2 days.
- **Practice services (`practice.py`):** `practice://<service>` monitors are answered in-process, no network: website, login, booking-api (a slow answer now and then), payments-api (7-minute outages every few hours), search-api (often slow), partner-api (flaky, 502s), shipping-api, images-cdn. The dice are seeded by service + monitor + the check's MOMENT, so the same check always gets the same answer; `?down=<time>&for=<minutes>` in the address adds an outage window. A practice timeout takes no real time. The address after `?` is hidden on pages (`monitor_address`).
- **Demo (`seed.py`, `views/demo.py`):** "Lakbay Travel", run by Rina Bautista (made up): 8 practice monitors, `.invalid` email, a random `session_version`, can't change its account, can only add practice monitors, deleted with its workspace after 24 hours (`seed.purge`, also by the timer). At most 20 demos at once, 10 per network an hour (not with `--debug`). **The demo's past is replayed, not written by hand:** `build()` (quick, in the Try Demo click) dates the monitors' first check 3 hours ago, sets `workspace.replaying` and queues a `demo_history` job, which runs `worker.simulate(..., workspace_id=..., direct=True)` through the real scheduler, checks and incident code (`direct`: due checks run straight away instead of as queued jobs, about 4 ms a check locally; re-checks still use the queue). While `replaying`, `queue.in_scope()` keeps the live crew away; the Dashboard shows a banner and reloads (`/demo/replay.json`). The Payments API had a 7-minute outage 105 minutes before the visitor came (a finished incident), and the Shipping API goes down 25 minutes before and comes back 30 minutes after (an open incident that closes while they watch). **Every page the demo can open must show an example, so add sample data with every new feature** (`tests/test_demo.py::test_every_page_of_the_demo_shows_an_example`). Hooks: `seed.extras` (before the replay), `seed.after_replay`.
- **Metrics (`metrics.py`, `rollups.py`, `views/numbers.py`), the metrics lesson:** uptime = good checks / counted checks (counted leaves out `our_side`; gaps are reported as "not made"). Every 5 minutes one worker queues a `rollups` job that RECOMPUTES each closed hour since the last run (and the one before, for late re-checks) from the raw checks into `rollups` rows (period `hour`, UTC; UNIQUE monitor + period + start), and each workspace's today and yesterday (period `day`, the workspace's own day, `local_midnight`/`day_starts` handle daylight saving) from the hour rows. Recomputing, not adding on, makes it safe to run twice. A recompute only replaces rows of monitors that have checks in that period (a demo's history has none). `rolled_until` (a `timers` row) says how far the hours are done; `done_until()` falls back to two days ago before the first run. Percentiles: rollups hold a histogram (`b0..b20`, `BUCKET_EDGES` on a log scale) because percentiles can't be averaged but histograms can be added; `percentile_of()` reads one off a merged histogram (an estimate, shown with ≈); windows of two days or less read the raw checks for exact values, with hourly rollups for hours before a monitor's first raw check in the window (`short_window`). Longer windows add day rows, today's hour rows and the raw checks since `rolled_until` (`window`). Raw checks are kept 14 days, hour rows 90, day rows 400 (`rollups.tidy`).
- **Charts (`charts.py`, `_numbers.html`):** server-drawn SVG geometry; the monitor page's Numbers section has period tabs (24 Hours, 7 Days, 30 Days, 90 Days; links end in `#numbers` so the page keeps its place), stat boxes (uptime, p50, p95, p99, incidents and downtime), the response-time chart (p50 as a 2px line, p95 as a 10% wash of the same hue, a `<title>` hover label per bin, and a data table), "Where the Time Goes" (24-hour averages of each part) and the 90-day uptime strip. Dashboard tiles have a sparkline of the last 30 checks (a failed check drops to the bottom) and the 24-hour uptime. **Colours were checked with the dataviz validator** against the cards (#ffffff / #0e1c16): response time is ONE hue, blue `--chart-1` (green means "up"); the check's parts are categorical slots 1-4 in order (DNS blue, connect orange, TLS aqua, wait yellow; the light aqua and yellow are below 3:1, so the parts are always labelled with their times); the uptime strip uses the status colours `--status-good/-warning/-critical`, which fail red-green colour blindness on their own, so a worse day is also a SHORTER bar (100% / 62% / 34% high), with a worded legend and a table. Change both dark blocks together.
- **The demo's older past (`history.py`):** before the replayed 3 hours, `seed.extras` writes hour rows for 7 days (every slot answered by the practice script) and day rows for 90 days (48 sampled answers a day, plus the exact outage minutes), and an `Incident` for every past Payments API outage (every 3 days). Nothing there is a raw check.
- **Alerts (`alerts.py`, `senders.py`, `crypto.py`, `views/alerts.py`), the alerting lesson:** `incidents.on_open/on_resolve` call `raise_alert()`, which makes one `Alert` per enabled `Channel` (UNIQUE incident + channel + event + seq: never the same alert twice) and queues a `deliver_alert` job. `deliver()` counts and COMMITS the try before the network call, then the sender answers `Delivered`, `TryLater` (429/5xx/timeout; becomes `queue.Retry`, with the service's Retry-After when it sends one) or `Rejected` (400/401/403/404/410; `queue.GiveUp`: never retry what can't work). A breaker per channel: 5 failures in a row rest it for 5 minutes (`paused_until`; its alerts `Defer`, using no tries); a Retry-After also rests it. Dead letters show on the Crew page. Senders: Discord and Slack webhooks (only their own addresses are accepted, `senders.DISCORD`/`SLACK`, so a webhook can't point into a private network), Telegram (bot token; "find the chat" reads getUpdates, so the owner writes to the bot first), email through Brevo's HTTP API (`BREVO_API_KEY`, `BREVO_SENDER`), phone alerts by web push (`VAPID_*`, `flask make-vapid-keys`, `PushSubscription`, the service worker shows them), and the Practice Inbox (`PracticeMessage`, drawn like each service; it answers 429 now and then so retries show). Every HTTP call goes through `senders.OPENER` (tests swap it). Webhook addresses and tokens are encrypted with Fernet (`crypto.py`, `ENCRYPTION_KEY`, else from `SECRET_KEY`) and never shown again. Every "down" alert has a signed Acknowledge link (`/ack/<token>`, `tokens.make("ack", incident.id)`): opening it only shows the page (chat previews open links), the button POSTs; the incident page has "I'm on it" too. The demo's four channels are practice ones (`alerts.demo_channels`, before the replay, so its replayed incidents fill the inbox); the demo can only add practice channels.
- **Smarter checks (`rules.py`, `certificates.py`, `heartbeat.py`):** the probers live in `rules.py` (`checking.PROBERS` per kind). HTTP monitors may have rules in `monitors.assertions` (`contains`, `not_contains`, `json_path` + `json_value` with dot paths into lists, `header`); a broken rule is a failed check (`error_kind` "assertion"). `slow_ms`: a good but slower answer is a Slow Beat (`checks.slow`) and the monitor shows a Weak Pulse (still up for uptime). `sleepy`: wait up to 90 s for a free-plan site to wake (the form then needs an interval of 2 minutes or more). TCP monitors (`tcp://host:port`, `probe.check_tcp`: up = the connection opened, nothing sent; the same private-network guard). Heartbeat monitors: a secret address `/hb/<token>` (no login, no CSRF, 30 pings a minute) that the owner's job calls; a ping is a good check and sets `next_check_at` to ping + interval + grace; if that check falls due, it IS the failure ("No ping since ..."), with `confirm_tries` and `recover_tries` of 1. Their pages show the address, a curl line and Send a test ping (no Check now, no response times). Certificates: every https check keeps the certificate's end date (`cert_expires_at`, `cert_issuer`); warnings at 14, 7, 3 and 1 day go out once each (`cert_warned_days`; a renewal resets it) as alerts without an incident (`alerts.raise_monitor_alert`), and the monitor page shows a banner. The demo has examples of each: a speed limit on the Search API, a JSON rule on the Booking API, the Images CDN's certificate running out in 9 days (`?cert=` in its practice address), and a "Nightly backup" heartbeat with two weeks of pings and one missed night (`heartbeat.demo_heartbeat`).
- **Alert rules (`alert_rules.py`, `/monitors/<id>/alerts`):** routing in `monitor_channels` (level 1: its alerts; none chosen = every channel; level 2: only the escalation). `incidents.on_open/on_resolve` call `alert_rules.on_open/on_resolve` (they replaced stage 5's plain hooks). Once a minute one worker (a timer) runs `check()`: reminders every `remind_every_m` while an incident is open and unacknowledged (`reminders_sent`, seq 1..10), one escalation after `escalate_after_m` (`escalated_at`) to level-2 channels, and settling flappers. FLAPPING: when a monitor opens its 3rd incident within 30 minutes, one "flapping" alert goes out and its down/up alerts are held (`monitors.flapping`) until it stays one way for 15 minutes: then "settled" (it ended up), or the held "down" alert (it ended down). A demo's replay runs the rules for its own workspace on its own timer row (`alert_rules:<id>`, deleted after the replay); the live run skips replaying workspaces (`queue.in_scope`). The demo: the Shipping API reminds every 15 minutes and escalates to Rina's phone after 20; the Payments API reminds every 30; the Old Partner API flaps for 30 minutes (`?flap=` in its practice address) and settles during the replay. New alert words go through `alerts.extra_words`.
- **Status pages (`status.py`, `views/status_pages.py`):** public pages at `/status/<slug>` (no login; the `public` blueprint) with the chosen monitors in order, each with an optional friendlier name (`status_page_monitors.label`), a PLAIN word (Up, Slow, Down, Maintenance: the public reads no heart-monitor words; Irregular shows as Up, so blips never reach the public), the 90-day strip, open incidents with their notes, maintenance that hasn't ended, the last 7 days' incidents, and an RSS feed (`/status/<slug>/feed.xml`, autoescaped XML). A slug is 3-60 small letters, numbers and dashes, unique. Incident notes (`incident_updates`: Investigating, Identified, Monitoring, Resolved; "Resolved" doesn't close an incident, good checks do) are written on the incident page. At most 5 pages a workspace.
- **Maintenance (`maintenance.py`, the Maintenance tab of Status Pages):** a window (title, from, to in the workspace's time zone, note, monitors). During it `incidents.before_judge` marks each check `resting` and moves the monitor to Resting, and judging stops: no incidents, no alerts. Resting checks are counted only as `resting` (never as checks, good checks or response times) in raw stats and rollups, so uptime leaves planned work out. An incident already open stays open. The demo has a finished window (Search, 3 days ago) and one planned for tomorrow at 2 AM (Booking API), a status page with friendly names, and notes on the replayed Shipping and Payments incidents (`status.demo_page`, `status.demo_notes`).
- **Insights (`insights.py`, `views/insights.py`):** each monitor has an uptime goal (`slo_target`, 99.9 at first; `GOALS`). Its error budget is what the goal allows to fail in 30 days, as time (99.9% = 43 minutes); FAILED CHECKS spend it, counted like uptime (`spent()`: 99.95% up spends 22 minutes), so uptime and budget always agree. The meter is green, then amber past half, red when spent, always with its words. Burn rate: the last 24 hours' failed share divided by the share the goal allows (1x = on budget). The page compares 7/30/90 days with the period before (in percentage points), lists incidents and downtime (`downtime()`: incident time inside the window), and exports CSV (UTF-8 with a BOM, for Excel). The weekly report: Settings turns it on (`workspaces.weekly_report`; turning it on counts this week as sent); an hourly timer job sends last week's numbers to every channel on Mondays at 8 AM, the workspace's time (`report_due`, `last_report_at`: once a week). The demo has goals of 99.95% (Payments) and 99.5% (Search), the report on, and last Monday's report in its inbox.
- **Installable app:** `static/site.webmanifest`, `/sw.js` (cache + offline page + push notifications), the "Install app" button in Settings and "Turn on alerts on this device" on the Alerts page (`app.js` subscribes with the VAPID public key and posts to `/alerts/devices` with the X-CSRF-Token header).
- **The words (`pulse_words.py`):** the app reads like a bedside heart monitor. States: Waiting, Steady, Weak Pulse, Irregular, Flatline, Paused, Resting; check results: Beat, Slow Beat, Missed Beat, Our Side. Every word has a plain-English note; templates show them with the `pulse()` / `monitor_state()` / `check_result()` macros in `_macros.html`, which put the note in a `title` and in hidden text for screen readers. Themed words name STATES; buttons and actions use plain words ("Check now"). Add new words to `pulse_words.py`, never straight into a template.
- **Times (`dates.py`, `formatting.py`):** the database holds naive UTC. Pages show the workspace's time zone (Settings). Functions that decide something about time take the moment as an argument instead of reading the clock. `ms` and `uptime()` format response times and uptime (uptime is cut, never rounded up to 100%); `check_time` shows seconds when a moment has them (re-checks).
- **Database:** SQLAlchemy 2.0 ORM (typed `Mapped[...]`), plain (not Flask-SQLAlchemy). `pulsecheck/db.py` makes one engine per app and one session per request: `db.session()`; code outside a request uses `db.new_session()` and closes it. SQLite locally (`instance/pulsecheck.sqlite`, WAL mode and a 30-second busy timeout), PostgreSQL (**Supabase**, psycopg 3) when `DATABASE_URL` is set. Supabase, not Neon: a check every minute would keep Neon awake all month and use up its free hours. PostgreSQL `numeric` is read as int/float (`PlainNumberLoader`). `workspaces` and `users` use `sqlite_autoincrement`, so a deleted demo's id is never handed out again.
- **Migrations: Alembic**, in `pulsecheck/migrations/`. `flask --app pulsecheck upgrade-db` runs them (with SQLite's foreign keys switched off during the run, so a table rebuild can't cascade-delete rows); Render runs it before gunicorn.
  - **To change the schema:** edit `models.py`, then `.venv\Scripts\alembic revision --autogenerate -m "what changed" --rev-id 000N`, **read the new file and fix it** (booleans default to `sa.false()`, never `sa.text('0')`, so PostgreSQL accepts them; a new NOT NULL column needs a `server_default`), and commit it. Never edit a migration that has run on the live site. `tests/test_migrations.py` fails if the models and the migrations disagree.
  - Every foreign key to a parent that is deleted in bulk needs an index that STARTS with that column, or the cascade scans the whole table (`checks` has it through its UNIQUE rule).
- **Deploy:** `render.yaml` (service `pulse-check`, free plan, Singapore; one gunicorn process with 8 threads; the crew is 4 threads inside it; `upgrade-db` before start) + Supabase (the **Session pooler** connection string: the direct one is IPv6-only) + the GitHub Actions timer (`TICK_URL`, `TICK_KEY` secrets). Environment: `SECRET_KEY`, `ENCRYPTION_KEY`, `TICK_KEY` (made by Render; never change the first two), `BASE_URL`, `DATABASE_URL`, and optionally `BREVO_API_KEY` + `BREVO_SENDER`, `VAPID_PUBLIC_KEY` + `VAPID_PRIVATE_KEY`. The owner is made from the PC with `create-owner` against Supabase. The steps are `docs/DEPLOY.md`, which also warns that checking other free Render apps often keeps them awake and uses up the account's 750 free hours.
- **Every page works without JavaScript.** `app.js` only adds extras. The CSP (`__init__.py`) has no inline scripts or styles, so **never use `style=""` or inline `<script>`**: sizes and colours are classes, or SVG attributes (the phase bar's widths).
- Commit messages and PR bodies go through files (`git commit -F`, `gh pr create --body-file`): PowerShell 5.1 breaks quotes in arguments.

## UI rules (the owner's priority is neatness)

- **Look: a bedside heart monitor**, drawn in CSS and small inline SVGs (no picture files), not just a palette: ECG paper (the faint grid on `body`: pink-red on cream in light, green on black in dark), the monitor screen (`.screen`: the login panel and the top of the menu), the bezel (`.bezel`, the menu's dark case), the trace (`_trace.html`: a heartbeat that sweeps across, flat and red while a monitor is down; still for `prefers-reduced-motion`), readouts (`.readout`, big JetBrains Mono numbers that glow on the dark monitor), pulse stamps (`.pulse-<tone>`, a pill with a lamp that beats for Steady), and a small beat under every page title (`title_trace()`). Colours are tokens on `:root`: monitor green `--accent` #047857 for buttons and links (white text 5.5:1; #34d399 with dark text in dark mode). Space Grotesk for headings, Inter for text, JetBrains Mono for numbers and labels, self-hosted in `static/fonts/`. Dark mode ("monitor on") is defined twice in `style.css` (device setting + the choice in Settings); change both blocks together (`tests/test_look.py` checks they match). Every text colour was checked for 4.5:1.
- **Messages are toasts** (`_toasts.html`, bottom right): `flash(msg)` is good news and fades after 6 seconds; `flash(msg, "error")` stays until closed.
- **Settings holds the controls, and the menus only navigate.** The theme (saved per device in `localStorage`; `theme.js` applies it before the page draws) is only on `/settings`. Log out is there too, and in the account menu at the bottom of the bezel.
- **No decorative emoji.** Icons are the line SVGs in `_icons.html`.
- **Page titles are bare:** `page_head(title)` from `_macros.html`, with no line of text under the title (only the small heartbeat).
- **Title Case** for the menu, page titles (`h1`), section headings, tabs, empty-state titles and anything that names a page or a state word. Small words (a, an, the, and, or, of, in, on, to, for, with, as, at, by) stay lowercase unless first. **Sentence case** for everything else: action buttons ("Add monitor", "Check now"), labels, hints, messages. The main button of a page is last on the right.
- Controls are the same height (`--control-height`) with bottoms aligned. Sizes in `rem`; the root font steps up at 1600 / 1920 / 2300px. Tabs are pills that wrap, never a sideways scroll; on phones, tables fit (`.fit-table`) rather than scroll.
- The bezel menu shows from 56rem up; below that a ☰ button opens it.
- The login page's left panel (logo, name, tagline, heartbeat, note) sits at the TOP of the panel, not in its middle (the owner's choice). On phones (under 52rem) it is a slim header: a 40px logo, the name and the tagline only (the heartbeat and the note are hidden), so the Log In card starts high.
- **Every PR must keep the README's pictures up to date (the owner's standing rule).** Screenshots live in `docs/screenshots/` and every one is shown in the README. If a PR visibly changes a page, retake the pictures with `docs/take_screenshots.py` (Playwright + Edge, borrowed from another project's `.venv`; its top comment has the steps; every picture comes from Try Demo, after its replay); if it adds a page or feature, add it there and a picture to the README. `tests/test_readme.py` fails if they disagree. In a PR description, link pictures with a full `raw.githubusercontent.com` address. Write the README in simple (A1-level) English.
